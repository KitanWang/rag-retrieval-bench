## 5. 融合策略扫描：混合检索为什么不一定更好

> 语料 20,000 篇 / 查询 100 条；`alpha` 是稠密分支权重（1.0 = 纯向量，0.0 = 纯 BM25）。

| 融合策略 | Recall@5 | MRR@5 | nDCG@5 |
| :--- | ---: | ---: | ---: |
| dense（纯向量） | 79.1% | 93.8% | 87.0% |
| bm25（纯稀疏） | 63.8% | 82.5% | 70.9% |
| RRF（k=10） | 78.6% | 90.6% | 84.4% |
| RRF（k=60） | 74.9% | 90.3% | 82.2% |
| RRF（k=100） | 74.7% | 90.3% | 82.1% |
| 加权融合（alpha=0.0） | 63.8% | 82.5% | 70.9% |
| 加权融合（alpha=0.2） | 69.0% | 86.5% | 75.9% |
| 加权融合（alpha=0.3） | 73.9% | 89.4% | 80.6% |
| 加权融合（alpha=0.4） | 76.5% | 92.0% | 84.1% |
| 加权融合（alpha=0.5） | 79.0% | 91.8% | 85.7% |
| 加权融合（alpha=0.6） | 80.0% | 92.1% | 86.4% |
| 加权融合（alpha=0.7） | 78.6% | 93.0% | 86.4% |
| 加权融合（alpha=0.8） | 79.7% | 93.2% | 87.1% |
| 加权融合（alpha=1.0） | 79.1% | 93.8% | 87.0% |

**最优：加权融合（alpha=0.6）（Recall@5 80.0%）**，比纯向量提升 +0.9 pp。

注意三点：
1. **最优融合不是等权**（alpha=0.6 而非 0.5）——两路检索器强弱差距大时，等权等于把弱的一路按同样的票数掺进来，把强路已排对的结果挤下去；
2. **RRF 的 k 值影响很大**：本数据集上 k=60 的 RRF（74.9%）甚至不如纯向量（79.1%），因为 k 越大、名次差异被压得越平，弱路的高名次噪声越容易挤掉强路的正确结果；
3. **本节数字没有被用来替换主表**——这是刻意的。主实验用的是 RRF k=60（社区默认值，未在本数据上调参），而这里的 alpha 是在**同一批评测查询**上扫描出来的。如果拿扫描最优值去替换主表，就是在测试集上调参，报告里的「提升」会虚高。正确做法是先在小规模验证集上定参数、再在评测集上一次性报告——本项目规模小，选择了「如实报告默认配置的结果 + 单独说明调参潜力」。

## 6. 向量后端基准（同一份向量、同一批查询）

> 语料 20,000 篇 / 计时查询 60 条 × 2 轮，k=10，嵌入模型 `BAAI/bge-small-zh-v1.5`。

| 后端 | 建索引 | p50 | p95 | top-1 与 FAISS HNSW 一致 |
| :--- | ---: | ---: | ---: | :--- |
| faiss-hnsw | 0.85 s | 0.235 ms | 0.338 ms | - |
| faiss-flat | 0.01 s | 0.848 ms | 4.905 ms | 是 |
| milvus-lite | 5.28 s | 1519.946 ms | 2006.213 ms | 是 |

> Milvus Lite 是进程内嵌入式实现，每次检索都要走完整的 gRPC/计划器路径；在纯 CPU、无独立索引服务进程的场景下，它比进程内 FAISS 慢三个数量级以上。**评测默认用 FAISS**，Milvus 后端保留用于验证「换回生产同款向量库后结论是否一致」。
