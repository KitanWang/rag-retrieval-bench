# RAG 检索策略对比基准

> 在**同一份中文语料、同一批评测查询、同一套指标**下，横向对比五种 RAG 检索方案：
> 朴素向量检索、BM25、混合检索（RRF）、混合检索 + 重排、策略路由。
>
> 目标不是刷榜，而是回答一个工程问题：**混合检索和重排到底值不值得上？贵多少？**

---

## 1. 为什么做这个项目

RAG 工程里最常见的一句结论是「混合检索 + 重排效果更好」，但**好在哪个指标、好多少、代价是什么**，
往往拿不出可复现的数字。这个项目把这些拆开量化：

| 要回答的问题 | 对应实验 |
| :--- | :--- |
| 纯向量检索的召回瓶颈在哪？ | `dense` vs `bm25` 的失败查询对照 |
| 混合检索真的能提升吗？ | `hybrid`（RRF 融合）vs 单路 |
| 重排带来多少提升、多少延迟？ | `hybrid_rerank` 的指标与 p50/p95 延迟 |
| 能不能只对部分查询付重排的钱？ | `router` 的级联路由 + 分支占比 |

---

## 1.5 实测结论（先看结论）

在 20,000 篇语料、300 条查询、纯 CPU 环境下的完整结果（详见 [`artifacts/RESULTS.md`](artifacts/RESULTS.md)）：

| 方案 | Recall@5 | nDCG@5 | p50 延迟 |
| :--- | ---: | ---: | ---: |
| 朴素向量检索 | **76.5%** | 87.4% | 0.6 ms |
| BM25 稀疏检索 | 61.5% | 72.2% | 0.4 ms |
| 混合检索（RRF k=60） | 72.6% | 83.3% | 1.6 ms |
| 混合检索 + 重排 | **80.9%** | 91.6% | 5684 ms |
| 策略路由 | 77.7% | 88.4% | 5054 ms |

**四个反直觉但可复现的结论：**

1. **「混合检索一定更好」是伪命题。** 等权 RRF 融合（72.6%）**反而低于纯向量检索**（76.5%）。
   原因是两路检索器强弱差距太大（76.5% vs 61.5%），等权融合等于把弱路按同样的票数掺进来。
   扫描 14 种融合配置后，最优是**加权融合 alpha=0.6**（80.0%），比等权高 7.4 pp，但只比纯向量高 0.9 pp。

2. **RRF 的 k 值比「用不用 RRF」更重要。** k=10 时 78.6%，k=60 时 74.9%，k=100 时 74.7%。
   k 越大、名次差异被压得越平，弱路的高名次噪声越容易挤掉强路的正确结果。

3. **重排带来 +4.4 pp，代价是 8882 倍延迟。** 这是本项目最需要被量化、也最常被含糊带过的一个 tradeoff。

4. **级联路由省了 45.6% 的总计算量，但只省了 11% 的 p50。**
   因为 54.3% 的查询都升级到了重排——**中位数仍然落在重排区间**。
   路由的收益体现在**总成本**（按查询量计费/排队的场景），
   而不是**单请求延迟**（用户能感知的场景）。这个区分很关键，很多方案介绍里不写。

> ⚠️ 关于「为什么不拿调参结果替换主表」：alpha=0.6 是在同一批评测查询上扫出来的。
> 用它替换主表就是在测试集上调参，提升会虚高。正确做法是先在验证集定参、
> 再在评测集一次性报告；本项目规模小，选择如实报告默认配置的结果，调参潜力单列一节说明。

## 2. 五种方案

| 方案 | 召回通道 | 说明 |
| :--- | :--- | :--- |
| `dense` | 稠密向量 | BGE 句向量 → FAISS HNSW（COSINE） |
| `bm25` | 稀疏词法 | jieba 分词 + 自实现 BM25 倒排索引 |
| `hybrid` | 稠密 + 稀疏 | RRF（倒数排名融合），对异构分数尺度不敏感 |
| `hybrid_rerank` | 混合召回 → 重排 | 召回 top-N 后用 cross-encoder 精排 |
| `router` | 级联 | 先跑两路廉价召回，**一致性低时才升级重排** |

路由规则不是按查询长度「猜」，而是看**两个廉价通道是否互相印证**：
若稀疏与稠密的 top-k 重合度高、top1 一致，说明两路都拿得准，直接融合；
若两路分歧，才交给 cross-encoder 仲裁。这样重排只为少数查询付费。

## 3. 快速开始

```bash
# 1. 环境（uv 管理，venv 建在工程目录下）
uv venv venv --python 3.12
uv pip install --python venv/bin/python -e ".[embed,dev]"

# 2. 下载并构建评测集（约 60MB 公开数据）
PYTHONPATH=src venv/bin/python -m ragbench.cli --config configs/default.yaml prepare

# 3. 跑五种方案的检索评测（纯 CPU 约 50 分钟，其中重排占 36 分钟）
PYTHONPATH=src venv/bin/python -m ragbench.cli --config configs/default.yaml retrieve

# 4. 生成 Markdown 报告
PYTHONPATH=src venv/bin/python -m ragbench.cli report
```

**为什么重排这么慢**：`bge-reranker-base` 是 cross-encoder，每条查询要对 50 个候选
逐对打分，CPU 上约 7 秒/查询。300 条就是半小时——这正是本项目要量化的「代价」。

只想快速看链路是否通，用冒烟配置（500 篇语料、20 条查询，几分钟出结果）：

```bash
PYTHONPATH=src venv/bin/python -m ragbench.cli --config configs/smoke.yaml all
```

单元测试：

```bash
venv/bin/python -m pytest tests -q
```

## 4. 评测集怎么来的

用公开中文检索数据集 **C-MTEB / DuRetrieval**（10 万篇语料、2000 条查询、9839 条相关性标注）。

为了在纯 CPU 上可跑，做了**带正例闭包的子采样**：

1. 抽 300 条查询（固定种子）；
2. 取这些查询的**全部** gold 文档，保证正例不被采样掉；
3. 用随机文档补齐到 20000 篇，作为检索干扰项。

> 这一步很关键：如果只是简单随机采样语料，正例可能被采掉，
> Recall 会被人为压低，方案之间的对比就失去意义。

## 5. 实测结果（k=5）

> 完整版见 `reports/RESULTS.md`（含生成质量与后端基准）。

| 方案 | Recall@5 | MRR@5 | nDCG@5 | Hit@5 | 延迟 p50 | 延迟 p95 |
| :--- | ---: | ---: | ---: | ---: | ---: | ---: |
| 朴素向量检索 | 76.5% | 94.7% | 87.4% | 97.3% | 0.6 ms | 0.9 ms |
| BM25 稀疏检索 | 61.5% | 85.4% | 72.2% | 90.3% | 0.4 ms | 0.7 ms |
| 混合检索（RRF） | 72.6% | 91.9% | 83.3% | 95.7% | 1.6 ms | 2.2 ms |
| 混合检索 + 重排 | 80.9% | 95.7% | 91.6% | 97.7% | 5684.5 ms | 8175.6 ms |
| 策略路由（级联） | 77.7% | 94.0% | 88.4% | 96.7% | 5053.5 ms | 8140.0 ms |

### 5.1 三个核心发现

**① 混合检索在这个数据集上并没有赢过纯向量检索**（Recall@5 72.6% vs 76.5%，-3.9 pp）。

这与「混合检索更好」的普遍经验相反，原因有三，我倾向第一个：
语料只有 2 万篇时 IDF 区分度不足，BM25 的排序噪声拖累了 RRF 融合；
本数据集的查询多为自然语言长尾问题，关键词匹配收益本来就小；
RRF 只用排名不用分数，当一路明显更弱时仍等权对待。

这不是「混合检索没用」的结论，而是「**在什么条件下它不划算**」的结论——
报告里把「按查询类型分层」「扩到 10 万语料」「改加权融合」列成了后续验证项。

**② 重排是唯一稳定带来正向收益的环节，但代价高了四个数量级**
（Recall@5 +4.4 pp、nDCG@5 +4.1 pp，而 p50 延迟从 0.6 ms 涨到 5684 ms，约 8882 倍）。

**③ 本地嵌入式 Milvus 不适合做批量评测。**

| 后端 | 建索引 | p50 | p95 | top-1 与 FAISS HNSW 一致 |
| :--- | ---: | ---: | ---: | :--- |
| FAISS HNSW | 0.85 s | **0.235 ms** | 0.338 ms | — |
| FAISS FlatIP | 0.01 s | 0.848 ms | 4.905 ms | 是 |
| Milvus Lite | 5.28 s | **1519.946 ms** | 2006.213 ms | 是 |

同一份 2 万条 512 维向量，Milvus Lite 比进程内 FAISS 慢**三个数量级以上**。
原因是 Milvus Lite 是进程内嵌入式实现，每次检索都走完整的 gRPC/计划器路径，
没有独立的索引服务进程。这直接改变了项目架构：**评测默认走 FAISS**，
Milvus 后端保留用于交叉验证「换回生产同款向量库后结论是否一致」。

复现命令：`PYTHONPATH=src venv/bin/python scripts/bench_vector_backends.py`

### 5.2 策略路由的真实价值

路由**不是提升效果，而是控制成本**：

| 路由分支 | 查询数 | 占比 | 平均延迟 |
| :--- | ---: | ---: | ---: |
| 混合检索（RRF） | 111 | 37.0% | 3.1 ms |
| BM25 稀疏检索 | 26 | 8.7% | 1.2 ms |
| 混合检索 + 重排 | 163 | 54.3% | 6614 ms |

若所有查询都走重排，总耗时 1984 s；实际 1078 s，**节省 45.6%**。

> ⚠️ 单看整体 p50 会得到相反结论：因为超过半数查询升级到重排，
> 中位数落在秒级区间。**节省体现在总耗时，不是中位数**——
> 这个坑我在报告里专门标注了，因为它是「用错指标就会得出错误结论」的典型例子。

### 5.3 一次真实的 bug：路由曾等于没路由

第一版路由把稠密与稀疏两个结果列表**首尾相接再截断**，
结果稠密分支占满名额、稀疏候选全被丢掉——「升级重排」其实只重排了向量结果。
这意味着路由的「升级」分支退化成了一次纯粹的向量重排，
两路融合的收益在升级路径上完全丢失——路由看似在「择优」，
实际只是「有时走融合、有时走向量重排」，谈不上策略。

修复后：先 RRF 融合成一路候选，升级分支再按 `rerank_candidates` 截断后重排。
两条不变量（**两路候选都要进入重排**、**候选数受显式配置约束**）都写成了回归测试
（`TestRouterCascade`），并验证过它们在旧实现下会失败。

> 另一个相关修正：最初把 `rerank_candidates` 设为 10，让 router 的重排代价只有全量重排的 1/5，
> 这样拿 router 和 `hybrid_rerank` 对比就**不公平**——两者不是同一个重排强度。
> 现已改回 50（与独立重排方案一致），router 的收益改为纯粹来自「少跑重排」，
> 代价（p50 不高、质量低 3.2 pp）如实呈现。

## 6. 生成质量评测（实测）

| 方案 | 忠实度 | 答案相关性 | 上下文精度 | 检索命中率 | 拒答率 |
| :--- | ---: | ---: | ---: | ---: | ---: |
| 朴素向量检索 | 99.8% | 81.7% | 67.0% | 98.3% | 18.3% |
| BM25 稀疏检索 | 99.7% | 73.3% | 52.7% | 86.7% | 28.3% |
| 混合检索（RRF） | 99.6% | 75.0% | 62.0% | 95.0% | 26.7% |
| 混合检索 + 重排 | 99.0% | **83.3%** | **70.7%** | 98.3% | 18.3% |
| 策略路由 | 99.0% | 80.0% | 65.7% | 95.0% | 20.0% |

### 6.1 生成质量的结论与召回指标一致

60 条查询 × top-5 文档，模型 `deepseek-v4.1-flash`，温度 0：

- **重排相关性最高（83.3%）**，与它最高的召回指标相互印证；
- **BM25 最差（73.3%）**，且拒答率最高（28.3%）——检索不到就直接拒答，这是**好的失败模式**
  （宁可说不知道，也不要编）；
- **忠实度普遍在 99% 以上**：这说明在这个数据集的问答形态下，**瓶颈在检索而不在生成**。
  换句话说，把重排加上去比换更大的生成模型更划算——这是一个成本决策依据。

> 拒答率不能单独看：BM25 拒答率高是因为召回差，而所有方案的忠实度都接近满分，
> 说明模型严格按「资料不足就说不知道」的约束在走，没有大面积幻觉。

## 7. 工程要点

- **BM25 用倒排索引**：打分复杂度是 O(查询词数 × 平均文档频次)，而不是 O(语料规模)。
  十万级语料上这是能不能跑完实验的分水岭，`test_inverted_index_matches_naive` 钉住了它与暴力实现等价。
- **向量缓存**：同一模型 + 同一文本只编码一次，改配置重跑时省下大量时间。
- **指标与检索解耦**：检索器只返回有序文档 id，指标统一在 `metrics.py` 计算，
  新增方案不需要改评测代码，也不会出现口径漂移。
- **报告自动生成**：README 里的数字全部来自 `artifacts/*.json`，杜绝手填数字对不上代码。
- **向量后端可切换且可基准**：`scripts/bench_vector_backends.py` 在同一份向量上对比
  FAISS HNSW / FAISS FlatIP / Milvus Lite，并校验三者 top-1 一致——
  性能数字不是拍的，是脚本跑出来的（见 `artifacts/backend_bench.json`）。

## 8. 目录结构

```

  config.py      实验配置（默认值 < YAML < 环境变量）
  data.py        数据集下载、子采样、qrels 归一化

  pipeline.py    建索引 → 跑评测 → 落盘

tests/           94 个单元测试
configs/         默认 / 冒烟两套配置
```

## 9. 已知局限

- **纯 CPU 环境**：BGE-M3 在 CPU 上实测 0.7 docs/s，20k 语料要 7 小时以上，
  因此默认配置用 `bge-small-zh-v1.5`（约 32 docs/s）。需要在 GPU 上换回 BGE-M3 只需改一行配置。
- **语料规模**：2 万篇是 CPU 上的折中。语料越小，稀疏检索越吃亏
  （干扰项少、IDF 区分度低），这一点在结论里必须如实说明。
- **重排成本**：cross-encoder 在 CPU 上约 7 pair/s，是整条链路最贵的一步，
  这也是级联路由存在的意义。
- **生成评测依赖外部 LLM**：结论中的相关性指标受模型版本影响（本次为 `deepseek-v4.1-flash`，
  温度 0）。LLM 判定失败时会降级为启发式，报告里会标出错误率。
- **忠实度接近满分不代表没有幻觉**：claim 级核查本身也用 LLM 做判别，
  若核查模型对「合理推断」过于宽容，忠实度会偏高。跨模型交叉核查是后续工作。
